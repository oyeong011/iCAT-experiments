# 워크로드 전환 후 변화 감지와 WAF 회복

- 작성: 2026-11-23 (승컴). 새 실험 없이 기존 로그만 썼다.
- 스크립트: `analysis/revision/recovery.py`
- 출력: `recovery.csv` (170행: 실행 × 단계)

## 1. 측정 기준 (계산 전에 정함)

| 항목 | 정의 |
|---|---|
| 전환 시점 | `kernel.log`의 `phase=<X> START` 표시와 `phase-<X>-start.time`. 두 값은 같은 실행 안에서 1초 이내로 맞는다. |
| 구간 WAF | `control-series.txt`(30초마다 누적 host와 GC 페이지 수)로 계산한 5분 이동창 WAF, 1 + ΔGC/Δhost |
| 기준 WAF | 같은 실행, 같은 단계의 **후반 50 %** 누적 WAF (그 정책 자신의 정상 상태) |
| 안정화 판정 | 5분 이동창 WAF ≤ 기준 × 1.05인 상태가 이어서 10분(20표본) 동안 유지된 첫 시점 |
| 회복 시간 | 안정화 시점 − 전환 시점. **최솟값은 약 300초다** (5분 창이 처음 채워지는 시점). |
| 변화 감지 시점 | 전환 뒤 첫 `WATGC_V2 reset` (4개 파티션 중 가장 빠른 것) |
| 재탐색 시작 | 위와 같다. 리셋하면 곧바로 재순회한다 (`online-v4-src/conv_ftl.c:448–470`). |
| 새 정책 선택 | 리셋 뒤 첫 `WATGC_V2 settled` |
| 재탐색 횟수 | 리셋부터 정착까지 판단 구간 수 (4개 파티션의 합) |

- **이 정의의 한계 1:** 고정 조합도 단계가 바뀌면 물리적인 과도 구간을 겪는다. 그래서 학습기의 **추가** 회복 시간은 같은 시기, 같은 부하의 고정 조합 회복 시간과 비교해서 읽는다.
- **이 정의의 한계 3 (11-23 고컴 교차검증 반영):** 이 기준은 "기준 × 1.05 이하"만 보는 단측 기준이다. 그래서 170개 단계 중 98개가 첫 창(약 300초)에서 바로 회복으로 판정된다. 고정 조합 값은 대부분 이 경우라서, 측정 가능한 최솟값으로 읽어야 한다.
  - `recovery.csv`에 양측 기준(|WAF/기준 − 1| ≤ 5 %, `recovery2_s`)과 "첫 창에서 바로 회복" 표시(`first_window`, `first_window2`)를 추가했다.
  - mixR 단계 C의 학습기 값(v4 422/570초, v3 1,056초)은 두 기준에서 같고, 첫 창 판정이 아니다.
- **이 정의의 한계 2:** 리셋은 부하 변화가 아니라 구간 잡음 때문에도 일어날 수 있다. 전환 직후 처음 일어난 리셋을 감지로 간주했다.

## 4. 재탐색 중 누적 CPU와 오버헤드

- **CPU는 미측정이다.** 9월과 10월 실행, 11월 mixY 실행 모두 계측하지 않은 빌드다.
- **추정값:** 재탐색 구간 수 × 판단 1회 평균 CPU (v4 6.18 µs, 11-14 자원 실험, FIO-Fast, n = 3)
  - mixR 단계 C의 v4: 80 × 6.18 µs ≈ **0.5 ms**
  - 단계 C의 dispatcher CPU 약 1,800초와 비교하면 무시할 수 있는 수준이다.
- **재탐색 비용의 실체는 CPU가 아니라 GC 페이지다.** v4 #1 기준으로 arm 47보다 GC를 380만 페이지(+1.9 %) 더 썼다 (표 2의 ᵃ, 계산값).
